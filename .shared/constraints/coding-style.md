# 通用编码与注释约束

> 只保留跨项目通用、长期稳定的约束。
>
> 项目、语言、框架自身的风格细节，优先遵循：
>
> 1. 项目现有代码、formatter、linter
> 2. `.shared/project/*.md` 中的项目约束（如果有）
> 3. 对应语言 / 框架的官方规范

## 基本原则

- 一致性优先于个人偏好；修改保持聚焦，不顺手扩散风格或结构。
- 先靠命名表达意图，再用注释补充代码无法直接说明的信息。
- 优先简单方案；没有明确收益时，不增加抽象、封装或防御层。

## 命名

- 命名默认短而清晰，避免句子式长名。
- 对外接口、跨模块名称可略长但要准确；局部变量和方法内符号更强调简洁。
- 允许使用社区常见或团队稳定共识的缩写；避免只在局部自创、难以理解的缩写。
- 局部作用域可省略重复上下文；例如 `getHotelRoomDevice()` 内优先 `device`，而不是 `hotelRoomDevice`。
- 同一目录、模块或抽象层内保持一致，不混用多套命名方式。

## 注释

- 注释只写代码本身难以表达的信息：为什么、约束、权衡、兼容性、边界假设、副作用。
- 关键分支、反直觉实现、兼容性补丁需要注释；平铺直叙的代码不补注释。
- 中文团队上下文默认使用简体中文注释；若项目明确要求英文或面向外部协作，以项目约定为准。
- 修改代码时同步更新注释；删除失效注释和注释掉的废弃代码。
- 优先写在代码上方，少用行尾注释。
- 对外 API、复杂副作用、异常约定，可按语言习惯补文档注释；简单内部实现不强制。

## 结构与调用链

- 保持调用链尽量短；单一调用点通常不值得额外包一层。
- 避免纯转发封装、重复校验、过度防御。
- 输入格式校验尽量放在边界层；同一事实已在上游校验后，下游默认信任，不重复做同类校验。
- 业务不变量放在真正拥有该规则的那一层，不因上游已校验就放弃约束。
- 分层交互优先相邻层调用；避免深层直接跨层回调上层。确需反向通知时，使用明确且稳定的接口、事件或协调层。

## 文档与测试

- 仅在对外接口、关键约束、使用方式明显变化时，补最小必要文档。
- 默认不主动新增单元测试；仅在用户明确要求、缺陷复现需要，或项目原本已有对应测试体系时再补充。
- 若仓库已有相关测试，改动后应同步更新并恢复通过。
- 测试尽量小而聚焦，直接覆盖本次改动的主要风险点。

## 诚实原则

- 只陈述实际完成的修改，以及实际运行过的验证。
- 未运行测试、构建或脚本时，明确写“未运行”或“未验证”。
- 预期结果、推断结论、实际观测分开表述，不将推断描述成事实。
