# /commit

代码提交命令（手动触发）。

## 核心要求
- 仅在用户显式输入 `/commit` 时执行
- 提交前先检查 `staged` / `changes` / `untracked`，必要时再看完整 diff
- 若改动跨多个关注点，先拆成多个小提交
- 提交前必须先做 diff + 最小验证
- 提交计划中给出类型建议：`feat` / `fix` / `refactor` / `docs` / `test` / `chore`
- 默认先说明拟提交范围、提交信息与待确认事项，再执行提交
- 暂存时优先精确到文件路径，避免无差别 `git add .`
- 若发现与当前任务无关的已暂存文件，先提示并确认是否纳入本次提交
- 默认不执行 push，尤其不主动建议 `git push --force`
- 若采用“先业务改动，再 docs(session)”双提交，第二次提交前必须回填业务提交锚点

## 轻量执行顺序
1. 盘点工作区状态，确认提交边界与是否需要拆分
2. 运行最小必要验证；若未验证，明确说明未验证项与风险
3. 先给出本次提交计划：状态摘要、建议批次、拟用 label 提交信息、待确认事项，再在用户确认后执行
4. 提交后输出 `commit hash` 与验证摘要

## 提交信息约定
- 默认使用 label 风格：`type(scope): 中文标题`；若无合适 `scope`，使用 `type: 中文标题`。
- `type` 默认从 `feat` / `fix` / `refactor` / `docs` / `test` / `chore` 中选择；若项目有更强约束，优先遵循项目约定。
- `scope` 只在确实有助于区分模块时使用；不要为凑格式硬加，也不要省略后退回纯中文无 label 标题。
- 同一仓库、同一分支、同一批次内尽量统一使用 label 风格，避免 label 与非 label 混用。
- 仅在用户明确要求或项目已有强制历史格式且不适合迁移时，才允许继续沿用非 label 标题。
- `session` / 文档回填类提交优先使用 `docs(session): ...`、`docs(commands): ...` 这类形式。
- 一次提交只表达一个主题，不把文件列表或实现细节堆进标题。

## 常见暂停条件
- 无法判断哪些文件属于本次提交
- 同一文件同时存在 staged 与未暂存修改，且边界不清晰
- 验证失败且无法快速确认是否与本次提交相关

## Session 锚点检查
- 若提交包含 `.shared/session/*.md`，必须检查“产出批次（提交锚点）”相关条目是否已填写真实 hash
- 若仍是 `提交: -`，且上一批次刚提交了业务改动，必须先回填 `提交: <commit-hash> <commit-subject>`
- 若本次提交只是在提交 session 文件自身，允许该 session 为“自身这一笔”保留 `提交: -`
- 不要求为了回填 session 自身再做第三次提交；除“session 文件自身”外，其他批次条目都应写真实 hash

## 当前项目工件关系
- 若上下文已经在 `.shared/session/*`、`.shared/project/*`、`research/*` 中充分记录，提交信息不需要重复冗长背景
- 默认不提交 `.tmp/*` 临时工件，除非用户明确要求保留证据
