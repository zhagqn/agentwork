# /commit

代码提交命令（手动触发）。

## 核心要求
- 仅在用户显式输入 `/commit` 时执行
- `/commit` 默认只生成提交计划并等待用户确认；用户输入 `/commit` 本身不等于授权立即暂存或提交
- 提交前先检查 `staged` / `changes` / `untracked`，必要时再看完整 diff
- `staged` 是用户的提交和 review 边界；非 `/commit` 流程不得主动 stage、unstage 或清空 staged 区
- 提交边界默认保守：只能提交能明确归属到当前批次意图的文件；无法明确归属、只是“顺手可回填”、或与标题语义不完全一致的文件，必须留在工作区并单独提示
- 若改动跨多个关注点，先拆成多个小提交
- 提交前必须先做 diff + 最小验证
- 提交计划中给出类型建议：`feat` / `fix` / `refactor` / `docs` / `test` / `chore`
- 默认先说明拟提交范围、提交信息与待确认事项，并停在等待确认状态
- 暂存时优先精确到文件路径，避免无差别 `git add .`
- 对 untracked 文件更保守：除非计划中逐项列出并说明归属，否则不要纳入提交
- 用户确认执行后，暂存和提交必须作为同一连续动作完成；不要只暂存不提交，也不要在 staged 区留下半成品状态
- 若发现与当前任务无关的已暂存文件，先提示并确认是否纳入本次提交
- 若同一文件同时存在 staged 与 unstaged 修改，默认保持边界不动；除非用户明确要求，否则不要用 `git add` / `git restore --staged` 改写该文件的 staged 状态
- 默认不执行 push，尤其不主动建议 `git push --force`
- 若采用“先业务改动，再 docs(case)”双提交，第二次提交前必须回填业务提交锚点

## 轻量执行顺序
1. 盘点工作区状态，确认提交边界与是否需要拆分
2. 运行最小必要验证；若未验证，明确说明未验证项与风险
3. 输出本次提交计划并停住：状态摘要、建议批次、拟暂存范围、明确排除/待确认文件、拟用 label 提交信息、待确认事项
4. 用户确认后，只执行已明确确认的一个批次；多批次默认逐批确认、逐批执行
5. 提交后输出 `commit hash` 与验证摘要

## 默认交互边界
- 第一轮 `/commit` 只做计划，不提交。
- 只有用户明确回复继续执行、确认提交、按该计划提交等确认语义后，才进入暂存和提交。
- 若用户在同一条消息中明确要求“直接提交 / 无需确认 / 按合理方式提交并同步 Case”，仍应先给出计划；除非同时给出明确的免确认授权，否则按默认两阶段执行。
- 多批次提交时，计划中必须说明每批范围与顺序；默认一次只执行一个批次，并在每个批次提交完成后回显 hash、剩余变更与下一批拟提交范围，再等待用户确认下一批。
- 即使用户确认了整体计划，也不要把“整体方向确认”理解为允许连续提交所有批次；只有用户明确说“连续执行全部批次 / 不再逐批确认”时，才可以按整套计划连续提交。
- 每批提交前必须重新读取 `git status` / staged 状态，确认即将暂存的路径仍只属于该批次；若出现新增或归属不清的路径，先暂停。

## 提交信息约定
- 默认使用 label 风格：`type(scope): 中文标题`；若无合适 `scope`，使用 `type: 中文标题`。
- `type` 默认从 `feat` / `fix` / `refactor` / `docs` / `test` / `chore` 中选择；若项目有更强约束，优先遵循项目约定。
- `scope` 只在确实有助于区分模块时使用；不要为凑格式硬加，也不要省略后退回纯中文无 label 标题。
- 同一仓库、同一分支、同一批次内尽量统一使用 label 风格，避免 label 与非 label 混用。
- 仅在用户明确要求或项目已有强制历史格式且不适合迁移时，才允许继续沿用非 label 标题。
- Case / 文档回填类提交优先使用 `docs(case): ...`、`docs(commands): ...` 这类形式。
- 一次提交只表达一个主题，不把文件列表或实现细节堆进标题。

## 常见暂停条件
- 无法判断哪些文件属于本次提交
- 文件能被技术上回填或一起提交，但无法从当前提交标题和批次目标中自然归属
- 同一文件同时存在 staged 与未暂存修改，且边界不清晰
- 验证失败且无法快速确认是否与本次提交相关
- untracked 文件未在计划中逐项说明来源和归属
- 多个 `.shared/case/*.md` 同时变更，但当前 active Case 或提交标题只覆盖其中一部分

## Case 锚点检查
- 若提交包含 `.shared/case/*.md`，必须检查“产出批次（提交锚点）”相关条目是否已填写真实 hash
- 若仍是 `提交: -`，且上一批次刚提交了业务改动，必须先回填 `提交: <commit-hash> <commit-subject>`
- 若本次提交只是在提交 Case 文件自身，允许该 Case 为“自身这一笔”保留 `提交: -`
- 不要求为了回填 Case 自身再做第三次提交；除“Case 文件自身”外，其他批次条目都应写真实 hash
- Case 回填默认只处理当前 active Case，或用户明确指定的 Case 文件。
- 不要因为另一个 Case 也引用了同一业务提交，就自动把它纳入当前 `docs(case)` 提交；这类文件应作为独立候选批次展示，并等待单独确认。
- 若一个 `docs(case)` 提交需要包含多个 Case 文件，提交计划必须逐个说明每个 Case 的归属理由，并获得用户对这一批范围的明确确认。
